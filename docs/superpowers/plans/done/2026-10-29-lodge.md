# lodge version 0.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A command-line tool and read-only local viewer through which agents record and read a project's decisions and specification entries in one defined format, with feedback on writes and a check that gates publication.

**Architecture:** A pure `core` (format, applying drafts, derived facts, the check, feedback, search, level views) under an `app` layer of operations behind three ports (Store, Clock, IdSource); adapters around it (`gitstore`, `cli`, `viewer`, `hook`) wired only in `main.py`. Records are Markdown files with a YAML header in the project's own git repository, either in the working checkout or on a dedicated branch written with git plumbing, never through a checked-out worktree.

**Tech Stack:** Python 3.12 or later, uv, PyYAML (only runtime dependency), pytest, mypy (strict), Ruff, Vulture; standard library `http.server`, `tomllib`, `argparse`, `subprocess` for git, `importlib.resources` and `importlib.metadata`.

**Spec:** `docs/superpowers/specs/2026-10-29-lodge-design.md` (approved 2026-10-29). Executors read it before their task; where this plan and the spec disagree, the spec wins and the disagreement is reported.

**Reviews:** plan reviewed 2026-10-29 from two angles (fidelity and feasibility; structure and risk), all findings answered in this version.

## Global Constraints

- `requires-python = ">=3.12"`; `pyproject.toml` and `uv.lock` committed; `uv sync` reproduces the environment.
- Runtime dependencies: PyYAML only. Dev group: pytest, mypy, ruff, vulture, types-PyYAML.
- Source layout: code in `src/lodge/`; the repository's own records in `lodge/` at the root (dogfooding), so code and data never share a path.
- Packages, allowed imports, and front doors exactly as the spec's Structure section, enforced by Task 1's structure test.
- `core` imports only `dataclasses`, `enum`, `typing`, `collections.abc`, `re`, `hashlib`, `datetime`, `tomllib`, `functools`, `itertools`, `json`, `yaml`, and its own modules; `app` imports the same plus `core`; neither names `now`, `today`, `utcnow`, `fromtimestamp`, `open`, `input`, or `print`.
- I/O confinement (LODGE-5, the author's ruling): `subprocess` only in `gitstore`; reading files only in `gitstore` (records, `.lodge.toml`) and `cli` (draft files named on the command line); `importlib.resources` for package data in `cli` and `viewer`; `hook` reads stdin only.
- No module over 300 lines, tests included.
- mypy `strict = true`; Ruff `line-length = 100`, `select = ["E", "F", "W", "I", "B", "UP", "SIM", "RUF", "TID", "PLC0415"]`, `flake8-tidy-imports.ban-relative-imports = "all"`; Vulture `min_confidence = 60` with `vulture_allow.py`.
- `scripts/check.sh` runs, in order: `ruff format --check`, `ruff check`, `mypy`, `vulture`, `pytest -q`, and from Task 13 on `lodge check --gate`; every task ends with it green.
- Git in tests: every fixture sets `GIT_CONFIG_GLOBAL` to an empty file, `GIT_CONFIG_NOSYSTEM=1`, a fixed identity, and `git init -b main`.
- Public from the first commit: no personal paths, machine names, or specifics of the first user in code, tests, or user-facing text; examples use a made-up project.
- User-facing text in British English, no em-dashes, Oxford comma.
- Length guidance defaults: title 100 characters, decision statement 80 words, specification statement 150 words, reasoning 1,000 words.
- IDs: `d-` or `s-` plus six characters of Crockford base32 lower case, alphabet `0123456789abcdefghjkmnpqrstvwxyz`.
- Exit codes: 0 success, 1 check failed or conflict, 2 usage or environment error; no traceback reaches the user, and the hook route always exits 0.
- Commits: `git -c user.name="Svenja Kernig" -c user.email=20756868+Kiibou-chan@users.noreply.github.com commit` with explicit paths, the message ending `Co-Authored-By: Claude <noreply@anthropic.com>`; push the build branch after each commit; never push `main`.

## Calls made in this plan (beyond the spec)

- **Settings** live in `.lodge.toml` at the root of the working checkout, not in the data (spec, Storage, updated with this plan). `core` parses `[length]` and `[import]`; `gitstore` parses `[store]`; `hook` parses `[hook]`; an unknown section or key is an error naming it.
- **Paths are fixed at creation** (`<id>-<slug of the first title>.md`); entries do not move between areas in 0.1; no file is ever deleted, so the store writes but never removes; checks 2 and 4 compare by ID, not path.
- **Area files** are drafts of their own (`kind: area`), added with `lodge add` and printed by `lodge draft area:<name>`; a new entry in an area that does not exist needs an area draft in the same add. Area title, intro, and order are presentation: they need no decision, and every add that changes them lists the change as a note.
- **New specification entries** get their ID first from `lodge id s`, so a decision draft can name them in `changes`; a decision draft omits `id` and `date`, which lodge fills (the date to the second, with offset, from the clock); a non-imported draft that sets `date` is refused.
- **Edits** go through `lodge draft <ref>`, whose output carries `base:` (the first 12 hex characters of the SHA-256 of the file in the current state); `lodge add` refuses an edit whose base no longer matches.
- **Imports** need `lodge add --import`; a new imported record whose `imported_from.file` is not listed in `[import] sources` fails the check; an imported decision that replaces or narrows a non-imported author decision is flagged like any agent decision.
- **Dates**: `date` must be ISO 8601 with an offset (an imported date-only value becomes `T00:00:00+00:00`); a new non-imported decision must be dated after every published decision it links to or shares an entry with.
- **Immutability**: every header key of a published decision is immutable; the reasoning of an author decision is immutable; an agent decision's reasoning may shrink, listed as a note.
- **The gate** fails only on problems that the after-state has and the published state does not; problems already published are printed as notes on every add, so one bad record never blocks everyone.
- **Related-decision feedback** fires when a decision has neither `replaces` nor `narrows` and `related` finds any, whether or not it has `changes`; the spec's wording ("changes nothing, replaces nothing, and narrows nothing") could never fire on a shared entry, its first criterion.
- **Branch mode** reads both states from the remote-tracking ref `refs/remotes/<remote>/<branch>` (so current equals published), fetched with an explicit refspec; it publishes with a temporary index and `commit-tree` whose parent is exactly the revision the change was built on, and pushes without force; a moved ref or a rejected push returns `REJECTED`, marks the store stale, and the app re-reads and re-applies, at most three times. No worktree, no rebase, no merge.
- **Checkout mode** reads the working tree as current and, as published, the tree at the merge base of `HEAD` with the first of `<remote>/<base>` and `<base>` that exists, or the empty state when neither does; it writes and stages files and never commits; it re-verifies under a lock that each file it overwrites still has the text it was built on.
- **Locks** are files created with `O_CREAT | O_EXCL` beside the git common directory, portable to Windows.
- **Freshness**: lodge writes its own fetch stamp file; a failed fetch serves the cached state and the freshness line says so.
- **Attachments** are placed by hand in 0.1 under `lodge/attachments/`; the store reads only record and area files; check 2 verifies that every listed attachment exists.
- **Dogfooding** records the spec's "Her decisions" only, each with her verbatim words where the spec or brainstorm holds them, otherwise her approval of the spec ("Approved", 2026-10-29 14:26).

## Review Focus

1. Two sessions add at the same time, in two clones or in two worktrees of one clone: the later push is rejected, lodge re-applies its drafts on the new tip, and both records end up published with a remote tip that passes the check (tests in Tasks 8 and 9).
2. A draft with broken YAML, a missing `---` fence, an unknown header key, a non-string scalar (`title: no`), or non-UTF-8 bytes: lodge names the file, the line where known, and the key, writes nothing, exits 2 (tests in Tasks 3 and 10).
3. A reference typed in another case or as a code (`item-1`, `D-3M8QK2`): `show` and `draft` resolve it; an ambiguous code is reported, never guessed (test in Task 6).
4. An edit draft made before someone else changed the same entry: `add` reports the conflict with both bases and writes nothing (test in Task 8).
5. lodge run outside a git repository, before `lodge init`, with a malformed `.lodge.toml`, or with the network down in branch mode: one sentence saying which, exit 2, no traceback; offline reads still answer from the last fetch and say so (tests in Tasks 9 and 10).
