On a store whose `.git/index` was written in the same second as many of the files (git 2.56.0 compares stat times at one-second granularity: files written in the second the index is written are "racily clean" and are re-read and hashed by every `diff-files`), every read re-hashes them. The bench stores are fresh clones (setup.py `git clone --no-hardlinks`; s90000 files by mtime second: 13,472 / 37,129 / 38,594 / 44,003 / 27,601, so about 27,600 files share the last second with the index write), every child runs with `GIT_OPTIONAL_LOCKS=0` (measure.py ENV, timings.md reproduction block), so no read refreshes the index, and nothing in measure.py writes it. The first index write came with `git checkout -- lodge` in bench_reads.py's `finally` (`mode in {"changed","chained"}`), which ran at the end of the chained experiment, i.e. after every matrix row and before the diagnostics stage. Order matches: matrix 0.477 (racy), diagnostics 0.336 (refreshed).
- Evidence, fresh clones of /var/tmp/lodge-bench/s90000 in my scratch dir, source-b1900 + venv python as measure.py, probe.py phases, `identity` stage / process total:
  * clone 1 (19.6k to 25.6k files in the index's second): identity 0.223-0.232 s, process 0.443-0.459 s, ordinary `show` seen 0.472, 0.452-0.461 s; after `git status`: identity 0.102-0.107 s, process 0.340-0.347 s.

  * clone 4 (19,660 files in the index's second): `git diff-files -z --name-only -- lodge` with GIT_OPTIONAL_LOCKS=0: 0.204 s and 0.207 s; after `GIT_OPTIONAL_LOCKS=0 git checkout -- lodge`: 0.042 s and 0.041 s.
